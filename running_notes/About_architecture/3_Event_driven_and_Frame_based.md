## Event drive accelerator structure and Event driven accelerator behaviour
A Comparative Analysis of Event-Driven and Frame-Based Accelerator Design Principles1. Introduction1.1. The Dichotomy in Accelerator DesignThe landscape of hardware acceleration for artificial intelligence (AI) and machine learning (ML) is largely characterized by two distinct design philosophies, driven by the nature of the data being processed and the underlying computational models. The dominant paradigm, frame-based acceleration, has evolved primarily to meet the demands of traditional Deep Neural Networks (DNNs), which typically operate on dense data structures like images or feature maps arranged in tensors. These accelerators prioritize high throughput for dense matrix multiplications and convolutions, often employing synchronous, massively parallel architectures.1 Their development has been fueled by the success of DNNs in domains like computer vision and natural language processing, where inputs are processed as complete frames or batches.Conversely, event-driven acceleration represents an emerging paradigm tailored for processing sparse, asynchronous data streams.3 This approach finds its roots in neuromorphic computing, drawing inspiration from the brain's efficient processing of information via discrete events or "spikes".4 Event-driven accelerators are particularly well-suited for Spiking Neural Networks (SNNs) and inputs from event-based sensors, such as Dynamic Vision Sensors (DVS), which inherently produce sparse data by encoding changes in the input rather than sampling the entire input space at fixed intervals.2 The primary motivation for event-driven architectures is energy efficiency, achieved by performing computation only when and where necessary, thus exploiting the inherent sparsity in activations or input data.71.2. Motivation and ObjectivesUnderstanding the fundamental architectural trade-offs and design principle differences between these two paradigms is crucial for advancing accelerator design. This report aims to dissect these differences, focusing specifically on the core computational units—Processing Elements (PEs)—and the memory hierarchy organization. To provide a concrete illustration of event-driven principles, the Seneca neuromorphic processor will be analyzed based solely on the information presented in the provided documentation.3 Seneca serves as a case study for how an architecture can be tailored to the unique demands of event-based processing.Furthermore, the report will investigate the applicability and inherent limitations of established cost modeling frameworks, such as ZigZag 10, which were primarily developed for frame-based DNN accelerators, when applied to event-driven systems. The unique characteristics of event-driven computation—sparsity, asynchronicity, and statefulness—pose significant challenges for conventional modeling approaches. Finally, leveraging the comparative analysis, this report will outline a conceptual pathway for adapting a baseline frame-based accelerator design to efficiently handle event-driven workloads.1.3. Finally, Section 6 concludes the report, summarizing the key distinctions and highlighting future research directions.2. Frame-Based Accelerator Design Principles: A Baseline2.1. Core Philosophy: Synchronous Dense Data ProcessingFrame-based accelerators are fundamentally optimized for processing dense tensors, such as images, video frames, or intermediate feature maps in conventional DNNs. Their core operational philosophy revolves around synchronous execution, where computations are typically performed on entire frames or batches of data in lockstep, often dictated by a global clock.3 The processing usually proceeds layer by layer through the network, assuming that most, if not all, data points within a frame are relevant and require computation.9 This approach is well-suited for algorithms where data dependencies are predictable and activity is dense across the input tensors.2.2. Typical ArchitectureThe architecture of frame-based accelerators reflects this philosophy, emphasizing high throughput for dense linear algebra operations.

Processing Elements (PEs): The computational core often consists of a spatial array of PEs, with systolic arrays being a common architectural pattern.12 These PEs are primarily designed as high-throughput Multiply-Accumulate (MAC) units, optimized for fixed-point or floating-point arithmetic on dense vectors or tiles of data. Dataflow strategies—such as weight stationary, output stationary, or input stationary—are employed to orchestrate data movement within the PE array, maximizing data reuse and minimizing off-chip memory access for these dense operations.11 The goal is to keep the MAC units continuously supplied with data to achieve peak computational throughput.


Memory Hierarchy: A typical memory hierarchy is designed to efficiently stage and deliver large blocks of dense data to the PE array. This usually includes small register files within each PE for immediate operands, shared L1 scratchpads or caches accessible by groups of PEs or the entire array for local data reuse (storing tiles of weights or activations), a larger shared L2 buffer (SRAM or eDRAM) acting as an intermediary between on-chip and off-chip memory, and high-bandwidth off-chip memory like DRAM or High-Bandwidth Memory (HBM) for storing the bulk of the model parameters and activations.10 Memory access controllers and Direct Memory Access (DMA) engines are optimized for predictable, high-bandwidth block transfers of dense tensors.


Control: Control logic in frame-based accelerators is typically synchronous and centralized or hierarchically distributed. It manages the PE array operations and orchestrates the movement of dense data blocks through the memory hierarchy according to predefined schedules. These schedules are often derived from the nested loop structures representing the DNN layer computations and the chosen dataflow strategy.10

2.3. Key Performance MetricsReflecting the focus on dense computation, the primary performance metrics for frame-based accelerators include raw computational throughput, measured in Tera Operations Per Second (TOPS) or Giga Operations Per Second (GOPS), energy efficiency (TOPS/Watt), and area efficiency (TOPS/mm²).18 These metrics emphasize maximizing the number of arithmetic operations performed per unit of time, energy, or silicon area, assuming a high utilization rate enabled by dense workloads.The design of frame-based accelerators is predicated on achieving efficiency through massive parallelism and optimizing data reuse for workloads that are predictable and dense. The architectural choices, from systolic PE arrays to memory hierarchies geared for block transfers, implicitly assume high activity rates across the data tensors, maximizing hardware utilization under these conditions.12 Any sparsity present is often handled through structured pruning techniques or specialized formats that maintain some regularity, rather than through fundamentally event-driven mechanisms.3. Event-Driven Accelerator Design Principles: The Seneca Case Study3.1. Core Philosophy: Asynchronous Sparse Event ProcessingIn contrast to the frame-based paradigm, event-driven accelerators like Seneca are architected to process sparse, asynchronous streams of events efficiently.3 This approach is particularly suited for SNNs, where information is encoded in the timing of discrete spikes, and for processing data from event-based sensors.7 The core principle is to activate computation only when an event (e.g., a spike) occurs, thereby exploiting the inherent sparsity often present in neural activations or sensor outputs to reduce energy consumption.3 Computation is reactive and data-driven rather than dictated by a fixed processing cadence applied to dense structures.3.2. Seneca's Hierarchical ArchitectureThe Seneca architecture, as described in the provided documentation, exemplifies several key design principles tailored for event-driven processing.3

Overall Structure: A Seneca core is built around several key components: a flexible RISC-V controller, a specialized Loop Controller with its Loop Buffer, an array of Neuron Processing Elements (NPEs), local Data and Instruction Memory (SRAM), an Event Generator, an interface to a Network-on-Chip (NoC) for inter-core communication, and a Shared Memory Pre-fetch Unit (SMPU) for accessing larger memory pools.3


Hierarchical Control (RISC-V + Loop Controller): A defining feature of Seneca is its two-tiered control system. A low-power Ibex RISC-V core (RV32IMC instruction set) acts as a flexible, general-purpose controller. It handles asynchronous event arrivals (interrupts), preprocesses incoming events (e.g., retrieving relevant local information, calculating destination addresses), manages memory allocation dynamically, implements event compression, packages events into micro-tasks for execution, and postprocesses outgoing events before NoC transmission.3 Complementing the RISC-V core is a custom, highly efficient Loop Controller. This controller fetches micro-tasks from a queue (Task FIFO) and orchestrates the parallel execution of micro-code instructions (stored in the Loop Buffer) across the NPE array in a SIMD fashion. This micro-code defines the specific sequence of operations for neural updates or other event-triggered computations. The Loop Controller is optimized for energy efficiency when executing these repetitive, nested-loop-like neural operations.3 This dual-controller system represents a direct architectural response to the conflicting needs of event-driven systems: requiring flexibility to handle unpredictable event timing and types (suited to the RISC-V core) while demanding efficiency for the common, loop-intensive neural computations triggered by those events (better handled by the specialized Loop Controller). This contrasts with the often more monolithic control structures found in frame-based accelerators designed for predictable, dense data flows.


Event Handling Flow: The processing pipeline is explicitly event-triggered 3:

An input event arrives via the NoC, interrupting the RISC-V controller.
The RISC-V preprocesses the event, retrieving necessary information (e.g., memory addresses for weights and neuron state) and creating a micro-task.
The micro-task is placed in the Task FIFO queue.
The Loop Controller fetches the micro-task and dispatches the corresponding micro-code instructions from the Loop Buffer to the NPE array.
NPEs execute the instructions in parallel, accessing Data Memory as needed to fetch weights and read/write neuron states.
If neural computations result in an output spike (e.g., neuron firing), the Event Generator detects this condition within the NPEs and creates an event packet.
The Event Generator interrupts the RISC-V core, which performs postprocessing (e.g., adding destination core addresses, compressing the event).
The RISC-V transmits the processed event via the NoC to other cores or potentially feeds it back into the local Task FIFO for further intra-core processing.



Handling Sparsity and Asynchronicity: Seneca incorporates specific features to manage the nature of event-based data 3:

Event-Triggered Computation: The entire workflow is initiated by incoming events, ensuring computation only happens when there is activity.
Globally Asynchronous, Locally Synchronous (GALS): While each core operates synchronously internally, communication between cores via the NoC uses an asynchronous protocol. This allows cores to operate independently based on event arrivals, avoiding the inefficiencies of a rigid global clock for asynchronous data.3
Lightweight Event Compression: The RISC-V controller can compress event data, reducing communication bandwidth, particularly useful when multiple correlated spikes occur.3
NoC Multicasting: The NoC supports source-based multicasting, allowing a single event packet to be efficiently delivered to multiple destinations, reducing overall network traffic in sparsely connected networks.3


3.3. Memory Hierarchy and Management in SenecaSeneca's memory system is structured and managed to address the specific challenges of event-driven workloads, particularly the handling of sparse data access and persistent neuron states.3

Memory Levels: The hierarchy comprises multiple levels with varying speed, size, and energy characteristics 3:

NPE Register Files: Small (e.g., 64x16-bit registers per NPE), fast (<1 ns access), and highly energy-efficient register-based memory within each NPE. Used for storing intermediate results and frequently accessed data like neuron states or weights for small neuron populations. Access is ~20x more energy-efficient than SRAM.3
Core Data Memory: On-core SRAM (e.g., 2 Mb) storing the bulk of the synaptic weights and neuron states (membrane potentials). Access latency is around 2 ns.3
Core Instruction Memory: On-core SRAM (e.g., 256 Kb) storing instructions for the RISC-V controller and micro-code for the Loop Buffer/NPEs.3
Shared Memory (Optional): Larger, potentially denser memory technologies like STT-MRAM (e.g., 36.8 Mb, ~25 ns read latency) or off-chip HBM (e.g., 64 Gb, ~135 ns latency) accessible via the SMPU to extend local storage capacity for very large networks.3



Data Storage: Synaptic weights and neuron states primarily reside in the Data Memory (SRAM) or shared memory. The RISC-V controller dynamically allocates memory, and the Loop Controller generates addresses for access during computation.3 Crucially, both weights and neuron states can be temporarily cached or held in the NPE register files to exploit temporal locality and minimize energy-intensive SRAM accesses.3


Event Data Handling: Incoming events are transient; they are not stored in the main data memory hierarchy. Instead, they arrive via the NoC, trigger the RISC-V controller, which then fetches necessary parameters (like addresses of weights and states) based on the event's source/type. This information is packaged into micro-tasks that drive subsequent computation in the Loop Controller and NPEs.3


Access Patterns and Optimizations: Unlike the predictable, dense block transfers in frame-based systems, memory access in Seneca is typically sparse, fine-grained, and triggered by asynchronous events. Accessing and updating neuron state for every incoming spike can be a major performance and energy bottleneck.7 Seneca employs several optimizations to mitigate these costs:

NPE Registers: Provide the fastest, lowest-energy storage for data reuse, critical for temporarily holding neuron states or weights.3
Spike-Grouping: A key optimization where the Loop Controller processes a group of incoming spikes targeting the same neuron(s) together. This allows the neuron state(s) to be fetched once from Data Memory, updated multiple times in the NPE registers based on the grouped spikes, and written back only once, significantly reducing SRAM read/write traffic.3
Shared Memory Pre-fetch Unit (SMPU): An optimized DMA unit that proactively fetches parameters (weights, states) needed for upcoming events (waiting in the Task FIFO) from the slower shared memory (STT-MRAM/HBM) into the local Data Memory (SRAM). This helps hide the higher access latency of the shared memory tiers.3
Event-Driven Depth-First Convolution: This technique, mentioned as an optimization for SENECA 7, specifically targets the large memory footprint associated with storing neuron states for entire feature maps in event-driven CNN processing. By processing data sequentially through multiple layers at a specific spatial location (pixel) before moving to the next, it drastically reduces the amount of intermediate neuron state that needs to be stored simultaneously, improving area efficiency.7


The design of Seneca's memory system is fundamentally shaped by the need to handle sparse, event-triggered accesses efficiently. Traditional memory systems optimized for dense block transfers would perform poorly under such access patterns. The multi-level hierarchy, particularly the fast NPE registers, allows frequently needed data (like neuron state during spike grouping) to remain close to the computation.3 Techniques like spike grouping directly amortize the high cost of accessing neuron state over multiple synaptic operations.3 The SMPU addresses the latency issue when scaling to larger models requiring off-core or NVM storage.3 Furthermore, the significant focus on managing neuron state—storing it in Data Memory, caching it in registers, reusing it via spike grouping, and reducing its footprint via depth-first convolution—highlights that handling this temporal state is a primary design challenge and a major contributor to cost (energy, area, latency) in event-driven accelerators like Seneca. 3.4. Processing Elements (NPEs) in SenecaThe Neuron Processing Elements (NPEs) form the core computational engine within Seneca, designed specifically for event-driven neural processing.3

Design and Functionality: Seneca employs an array of NPEs operating in a SIMD (Single Instruction Multiple Data) fashion under the control of the specialized Loop Controller.3 Each NPE contains its own register file (e.g., 64x16-bit) to facilitate local data reuse, minimizing accesses to the main Data Memory.3 Instead of executing fixed hardware functions continuously, NPEs execute sequences of instructions, termed micro-code, fetched by the Loop Controller from the Loop Buffer. This micro-code defines the specific operations required for different neuron models or event processing tasks.3


Event-Triggered Operation: A key distinction from frame-based PEs is that NPEs are reactive. They are activated by micro-tasks dispatched by the Loop Controller, which themselves are generated by the RISC-V core in response to incoming events.3 Computation within an NPE only occurs when there is a relevant event and associated micro-task to process, directly exploiting activation sparsity.3


Computational Capabilities: NPEs are designed to perform "special operations common among many neuron models".3 This implies functionality beyond the simple MAC operations dominant in frame-based PEs, likely including operations for integrating inputs into a neuron state (membrane potential), applying decay or leak, comparing the state against a threshold, and generating output spikes. Seneca's NPEs support various data types and precisions, including 4, 8, and 16-bit integers, as well as potentially logarithmic or floating-point representations.3 This flexibility is crucial for SNNs, where mixed precision can be used to optimize memory footprint and energy consumption while maintaining accuracy.3


Contrast with Frame-Based PEs: The differences are fundamental 3:

Activation: Event/micro-task triggered vs. clock/data arrival triggered.
Operation: Execution of flexible micro-code sequences for neuron dynamics vs. predominantly fixed MAC operations on dense data.
State: Inherently stateful (managing neuron potential) vs. typically stateless feedforward computation.
Control: Driven by Loop Controller dispatching micro-tasks vs. synchronous control managing dense data flow.
Sparsity: Explicitly handled via event-driven activation vs. implicitly handled (if at all) through structured data formats or dense computation.


Seneca's NPEs are therefore specialized computational units tailored for the reactive, stateful, and often mixed-precision computations inherent in event-driven neural models like SNNs. Their design diverges significantly from the high-throughput, stateless MAC engines optimized for dense matrix arithmetic in frame-based accelerators. 3.5. Summary of Unique Event-Driven Principles in SenecaThe analysis of Seneca, based on the provided documentation, reveals several core design principles unique to the event-driven paradigm:
Hierarchical Control: Balancing flexibility (general-purpose core for event management) and efficiency (specialized controller for neural computations).
Event-Triggered Computation: Activating processing units only in response to incoming events to exploit sparsity.
Stateful Processing: Explicitly managing and optimizing the storage and access of persistent neuron states.
Memory Optimizations for Sparsity: Employing techniques like register caching, spike grouping, and specialized convolution methods (depth-first) to mitigate the cost of sparse, stateful memory access.
Asynchronous Communication: Utilizing GALS and efficient multicast NoCs to handle asynchronous inter-core event transmission.
Flexible Compute Units: Using micro-coded, mixed-precision PEs capable of performing stateful neural operations beyond simple MACs.
4. Cost Modeling Considerations: Event-Driven vs. Frame-Based (ZigZag Context)Accurate cost modeling is essential for Design Space Exploration (DSE) of hardware accelerators, allowing designers to estimate performance and energy efficiency without resorting to time-consuming simulations or physical implementations. Frameworks like ZigZag have emerged as valuable tools for exploring the vast design space of traditional DNN accelerators. However, applying these frameworks directly to event-driven architectures like Seneca presents significant challenges due to fundamental differences in their operational principles.4.1. ZigZag Framework Overview for Frame-Based DNNsZigZag is a DSE framework specifically designed for optimizing DNN accelerators, with a strong focus on the memory hierarchy and dataflow.26
Purpose: It aims to rapidly estimate the hardware cost (energy, latency, area) of mapping a DNN workload onto a given accelerator architecture, enabling exploration of different architectural choices and mapping strategies.10
Methodology: ZigZag employs a memory-centric approach, representing the DNN computation (weights W, inputs I, outputs O) and data movement using a nested-for-loop format.10 It analyzes how these loops are tiled across different memory levels (loop blocking), the order in which loops are executed (loop reordering), and how computation is parallelized across PEs (spatial unrolling).10 A key feature is its ability to explore both "even" mappings (where all operands share the same tiling at a memory level) and "uneven" mappings (where operands can have different tiling strategies at shared memory levels), significantly expanding the searchable design space.10 Based on this mapping analysis, ZigZag estimates memory access counts, required bandwidth, data reuse, and PE utilization to derive energy and latency figures.10
Assumptions: The framework implicitly relies on several assumptions common to frame-based DNN processing 10:

Synchronous Execution: Computations proceed in a predictable, cycle-accurate manner determined by the loop structure and hardware clock.
Dense or Structured Data: The analysis primarily targets dense tensor operations, although some structured sparsity might be modeled if it fits the loop representation. It doesn't inherently model arbitrary, fine-grained sparsity.
Stateless Computation: The core operations modeled are typically stateless MACs, reflecting standard ANN layers.
Predictable Access Patterns: Memory accesses are assumed to follow patterns derivable from the loop structure and tiling strategy.


4.2. Challenges in Applying ZigZag to Event-Driven Accelerators (like Seneca)Directly applying ZigZag or similar frame-based cost models to event-driven accelerators like Seneca leads to inaccurate or incomplete estimations due to fundamental mismatches with the underlying assumptions.30
Data Sparsity: Event streams are inherently sparse and often unstructured temporally and spatially.9 ZigZag's loop-based analysis, designed for dense tensors, cannot easily capture the energy savings from skipping computations involving zeros (implicit in event-driven processing) nor the potential overheads associated with managing this sparsity (e.g., indexing, conditional execution).13
Asynchronicity and Data Dependency: Event arrival times are data-dependent and asynchronous, not tied to fixed loop iterations.3 The actual execution time and energy depend critically on when events occur and the resulting dynamic workload, which is difficult to capture in a static loop-based model. Performance can be highly variable and input-dependent.
Neuron State Management: A major component of SNN computation involves managing neuron state variables (e.g., membrane potential, synaptic traces).23 This involves frequent read/modify/write operations to memory, contributing significantly to energy consumption and latency.7 ZigZag's standard W/I/O operand model does not include representations for these dynamic state variables or the cost associated with their access and storage.23
Temporal Dynamics: SNNs and event-based processing inherently operate over time.23 Factors like spike timing, synaptic delays, and state decay influence computation and performance. Static loop analysis frameworks like ZigZag are ill-equipped to model these dynamic temporal effects.
Communication Patterns: Event-driven systems often rely on packet-based communication over a NoC, frequently employing multicast to deliver spikes to multiple destinations.3 Modeling the performance and energy cost of such asynchronous, potentially irregular, and multicast-heavy traffic patterns is significantly more complex than modeling the predictable block transfers common in frame-based systems.
Relevant Metrics: Traditional metrics like MAC operations or FLOPS become less meaningful. Event-driven systems are better characterized by metrics such as Synaptic Operations (SOPs), energy per SOP (often measured in pJ/SOP or fJ/SOP), event processing latency, spike throughput, and the energy/area cost associated with state memory.7
The fundamental operational differences—asynchronous, sparse, stateful, and event-triggered computation versus synchronous, dense, stateless, loop-driven computation—render direct application of models like ZigZag inadequate for accurately predicting the performance and energy of event-driven accelerators.30 The model fails to capture the sources of efficiency (sparsity exploitation) and the primary cost drivers (event handling overhead, state management, asynchronous communication) unique to this paradigm.4.3. Potential Adaptations and AlternativesAddressing the limitations of frame-based cost models for event-driven systems requires significant modifications or entirely new tools.

Extending ZigZag?: Adapting ZigZag would necessitate fundamental changes. It would need capabilities to model statistical sparsity, represent event queues and asynchronous triggering, incorporate explicit costs for neuron state access and storage, handle dynamic timing dependencies, and model asynchronous NoC traffic with multicast. This likely constitutes a major redesign rather than simple extensions.


Specialized SNN/Event-Driven Tools (STEMS): The emergence of tools like STEMS (Spatial-Temporal Mapping Tool for Spiking Neural Networks) highlights the need for specialized modeling frameworks.23 STEMS is explicitly designed for SNN mapping exploration and addresses key limitations of traditional models:

Stateful Modeling: It explicitly models neuron states as operands and accounts for their storage and movement costs.23
Temporal Dimension: It incorporates time as a dimension in the workload representation, enabling analysis of temporal data reuse and state evolution.23
Inter-layer Optimization: It explores mapping optimizations across layers (layer fusion/depth-first scheduling), which is critical for minimizing the significant data movement associated with neuron states in multi-layer SNNs.23
SNN Costs: It focuses on metrics relevant to SNNs, particularly minimizing data movement energy, acknowledging the high cost of state transfer.23
The existence and specific features of STEMS underscore that accurate modeling of SNNs and event-driven accelerators requires dedicated approaches that capture the unique aspects of statefulness, sparsity, and temporal dynamics, which are absent in conventional DNN cost models like ZigZag.7



Other Neuromorphic Simulators/Frameworks: A variety of other software tools and frameworks exist within the neuromorphic ecosystem, such as Lava (Intel) 41, PyNN 42, NEST 42, CARLsim 42, and tools associated with SpiNNaker.42 While invaluable for developing and simulating SNN algorithms and often providing interfaces to specific hardware platforms (like Loihi or SpiNNaker), many of these focus on functional correctness or detailed biological simulation rather than providing a general-purpose, architecture-level cost estimation and DSE capability comparable to ZigZag or STEMS for arbitrary hardware configurations.

5. Conceptual Design Path: Frame-Based to Event-Based AcceleratorAdapting a frame-based accelerator design for event-driven processing involves more than incremental changes; it requires rethinking core components to handle the fundamental differences in data representation, timing, and computation. This section outlines a conceptual two-step process.5.1. Step 1: Design a Baseline Frame-Based AcceleratorThe starting point is a conventional frame-based accelerator tailored for a specific workload (e.g., a target CNN).
Workload Definition: Specify the layers, tensor dimensions (input size, channels, filters, kernel sizes), and numerical precision (e.g., INT8, FP16).
Architecture Selection: Choose a PE array configuration (e.g., 16x16 PEs) and a dataflow strategy (e.g., output stationary) suitable for the dense workload.13
PE Design: Implement PEs primarily as MAC units with local registers for operands and accumulators.13
Memory Hierarchy Design: Size the on-chip buffers (L1 scratchpads, L2 global buffer) and determine off-chip memory bandwidth based on the data reuse patterns and throughput requirements calculated for dense tensor operations.10 Tools like ZigZag could potentially be used at this stage for initial DSE based on dense assumptions.10
Control Logic Design: Implement synchronous control logic to manage the PE array and orchestrate the scheduled movement of dense data blocks.
5.2. Step 2: Identify Key Modifications for Event-Driven AdaptationTransitioning this baseline design to handle sparse, asynchronous events (e.g., for an SNN version of the CNN) requires fundamental changes across subsystems:

Input Interface/Event Handling:

Replace the frame input buffer with an event queue or buffer capable of receiving asynchronous event packets (e.g., AER format).50
Add event decoding logic to extract information (e.g., source neuron ID, timestamp, payload for graded spikes) from incoming events.3
Implement logic to detect event arrival and trigger subsequent processing.



Control Logic:

Shift from synchronous, schedule-driven control to asynchronous, event-triggered control.3
Implement a flexible controller (analogous to Seneca's RISC-V) to handle event interrupts, preprocess events, manage memory (including state), and generate tasks.3
Implement an efficient task scheduler/dispatcher (analogous to Seneca's Loop Controller) to manage a queue of pending tasks and dispatch them to available PEs.3
Requires robust interrupt handling and queue management mechanisms.



Processing Elements (PEs):

Modify PEs to be idle until activated by a dispatched task/event.3
Augment PE functionality beyond MACs to include operations specific to the chosen neuron model (e.g., Leaky Integrate-and-Fire - LIF): state integration (accumulation), leak application (decay), threshold comparison, and state reset upon firing.3
Add spike/event generation logic within or associated with the PEs to create output events when neurons fire.3
Consider support for mixed precision if required by the SNN model.3



Memory Subsystem:

Re-design the memory hierarchy to efficiently store and access neuron state variables alongside synaptic weights. This likely requires significant dedicated storage for states, potentially dominating the memory footprint.3
Optimize memory access for sparse, potentially random patterns triggered by events. High bandwidth for dense blocks becomes less critical than low latency for fine-grained state/weight access.
Implement state caching mechanisms (e.g., using PE registers like Seneca's NPE RF) to reduce latency and energy for frequently accessed states.3
Consider adding logic to support optimizations like spike grouping to amortize state access costs.3



Network-on-Chip (NoC):

If a multi-core design, adapt the NoC for asynchronous packet switching suitable for event transmission.3
Implement efficient, low-overhead multicast routing if the SNN requires fan-out connectivity, as point-to-point routing becomes inefficient.3
Design appropriate flow control mechanisms to handle potentially bursty and unpredictable event traffic patterns.22


5.3. Highlighting Major Trade-offsThis adaptation process involves navigating significant trade-offs:
Flexibility vs. Efficiency: The need for flexible event handling and programmable neuron behavior (potentially via micro-code like Seneca) introduces overhead compared to hardwired, optimized frame-based pipelines.
Sparsity Benefits vs. Overheads: The energy saved by skipping zero-valued computations (inherent in event-driven processing) must compensate for the added energy and latency overheads of event decoding, task scheduling, asynchronous control, state memory access, and potentially lower average PE utilization if event rates are low or bursty.7 Fine-grained event processing can incur significant overhead per event.7
Memory Footprint: Storing neuron states can dramatically increase on-chip memory requirements compared to stateless ANNs, potentially becoming a major bottleneck.7 Techniques like event-driven depth-first convolution aim to mitigate this but add control complexity.7
Design Complexity: Implementing asynchronous control, event handling, stateful PEs, and potentially asynchronous NoCs significantly increases design and verification complexity compared to simpler synchronous, stateless frame-based systems.
The conversion from a frame-based to an event-driven accelerator is evidently not a minor adjustment but a fundamental architectural transformation. It necessitates redesigning the control fabric (from synchronous orchestration to asynchronous reaction), the compute units (from stateless MACs to stateful neuron emulators), the memory system (from dense tensor buffering to sparse state/weight management), and the communication infrastructure (from predictable block transfers to asynchronous event routing). Each modification directly addresses the core operational differences—data representation (dense vs. sparse events), timing (synchronous vs. asynchronous), and computation (stateless vs. stateful)—highlighting the distinct nature of the two accelerator paradigms.6. Conclusion and Future Directions6.1. Summary of Key DistinctionsThis report has contrasted the design principles of frame-based and event-driven accelerators, using Seneca as a specific example for the latter based on the provided documentation. The analysis reveals fundamental differences rooted in their core operational philosophies. Frame-based accelerators excel at high-throughput, synchronous processing of dense data, leveraging spatial parallelism (e.g., systolic arrays) and memory hierarchies optimized for block transfers. Their PEs are typically stateless MAC engines. In contrast, event-driven accelerators like Seneca are designed for sparse, asynchronous event streams. They employ event-triggered computation, often with hierarchical control balancing flexibility and efficiency. Their memory systems prioritize mitigating the high cost of sparse access and managing persistent neuron states through techniques like caching, spike grouping, and specialized dataflows. Their PEs are stateful, often micro-coded units capable of executing neural dynamics.6.2. Recap of Modeling ChallengesThe distinct nature of event-driven computation poses significant challenges for traditional cost modeling frameworks like ZigZag, which are built on assumptions of synchronous, dense, stateless processing. Key difficulties include modeling unstructured sparsity, asynchronous and data-dependent timing, the overhead of neuron state management, dynamic temporal effects, and irregular communication patterns like multicast. Consequently, specialized tools such as STEMS, which explicitly incorporate statefulness and temporal dynamics, are necessary for accurate DSE of SNNs and event-driven accelerators.6.3. OutlookThe field of accelerator design continues to evolve rapidly, driven by the demands of increasingly complex AI models and the need for greater energy efficiency. Several key directions are shaping the future:

Hybrid accelerators may offer a way to efficiently process mixed data types or leverage the benefits of sparsity selectively.9
In conclusion, while frame-based accelerators remain dominant for conventional dense DNNs, event-driven architectures like Seneca represent a distinct and increasingly relevant design paradigm optimized for the sparse, asynchronous, and stateful nature of neuromorphic computation. Continued innovation in architecture, modeling tools, underlying technologies, and benchmarking methodologies will be critical to unlocking the full potential of both approaches and potentially bridging the gap between them.

Modeling Event-Driven Accelerators for Dense ANNsWhile STEMS addresses the modeling of SNNs, another emerging area involves accelerators that apply event-driven principles, often borrowed from neuromorphic computing, to execute conventional ANNs. Hardware like SynSense's Seneca 92 exemplifies this trend, aiming for low-power, low-latency operation. Modeling such accelerators, even when they process dense ANNs, poses challenges for traditional frameworks like ZigZag/Stream due to fundamental differences in execution paradigm.3.1 Characteristics of Event-Driven Hardware (e.g., Seneca)Event-driven accelerators exhibit several key characteristics that distinguish them from traditional synchronous, frame-based designs:
Event-Triggered Computation: The defining principle is that computational activity is triggered by the arrival of input data events, rather than being dictated by a global clock signal advancing through a predetermined schedule based on loop iterations.2 In the context of ANNs, an "event" might correspond to receiving a non-zero activation value from a preceding layer or processing element. This fundamentally shifts performance dependency from static loop bounds to dynamic event rates and processing pipelines.
Potential Asynchronicity: Event-driven systems often facilitate or necessitate asynchronous operation, either between cores (Globally Asynchronous, Locally Synchronous - GALS, as in Seneca 95) or even within cores.65 Asynchronous design eliminates global clock overhead and allows components to process data as it becomes available, potentially improving average-case performance and energy efficiency.212 However, it introduces variability and makes performance analysis more complex, relying on factors like queueing delays and contention rather than fixed cycle counts.207
Event Handling Logic and Overhead: Dedicated hardware is required to manage the flow of events: receiving interfaces, decoding logic (to interpret event addresses or data payloads), event queues (e.g., FIFOs) to buffer events when processing units are busy, and controllers to dispatch events/tasks to the appropriate PEs.95 This event management infrastructure introduces an inherent overhead – both in terms of energy consumption (static and dynamic per event) and latency – for every event processed.64 This "event tax" is a fundamental cost component distinct from the core computation (e.g., MAC) and data movement costs. Seneca, for example, utilizes its RISC-V controller for event pre/post-processing and an Event Generator unit.95 Ignoring this overhead leads to inaccurate cost estimations.
Specialized Processing Elements (PEs): PEs in event-driven accelerators might be tailored for event processing. Seneca's Neural Processing Elements (NPEs) are SIMD units that execute micro-code sequences triggered by events, performing neuron updates or other computations.95 They might incorporate features like event buffering or optimized handling of grouped events (e.g., Seneca's spike-grouping reduces per-event overhead by processing multiple events targeting the same neuron together 93).
Memory Access Patterns: Data access from the memory hierarchy (which might involve local SRAM, shared memory like MRAM, or off-chip HBM 95) is triggered by the arrival and processing of events. Dataflow optimizations might be specifically designed for event-based processing, such as Seneca's event-driven depth-first convolution which aims to reduce intermediate state memory by processing events sequentially.93 Specialized units like Seneca's Shared Memory Pre-fetch Unit (SMPU) might be used to hide latency when accessing slower shared memory tiers based on queued events.95
Network-on-Chip (NoC) Design: Inter-core communication in event-driven systems often relies on NoCs optimized for low-latency transmission of small event packets.65 These NoCs might be asynchronous and often support efficient multicast mechanisms, as a single event (e.g., activation output) might need to be sent to multiple downstream PEs.65
3.2 Challenges vs. Synchronous Frame-Based Models (ZigZag Assumptions)Modeling these event-driven characteristics poses significant challenges for frameworks like ZigZag/Stream, which are built on assumptions derived from synchronous, frame-based DNN accelerators:
Synchronous Execution Assumption: ZigZag and Stream operate on a fundamentally synchronous, loop-driven execution model.125 Latency is calculated based on the number of cycles required to complete all iterations of the mapped loop nest, limited by the slowest resource (computation or memory bandwidth). Event-driven execution decouples computation from fixed loop iterations; latency becomes dependent on the dynamic flow of events through the system, including processing times and potential queueing delays.
Dense Data Computation Assumption: While extensions like Sparseloop adapt ZigZag for data sparsity in ANNs 37, the core ZigZag model assumes computation occurs for every point in the iteration space defined by the loops. Event-driven accelerators, however, only perform computation when triggered by an event. The fundamental difference is the trigger mechanism (event arrival vs. loop counter increment), which dictates the control flow and associated overheads, even if the underlying data or computation (like a MAC) is dense once triggered.
Ignoring Event Handling Overhead: Standard ZigZag cost models focus on the energy and latency of MAC operations and data movement between memory levels and PEs.122 They lack components to account for the energy and latency costs of the event handling infrastructure (queues, decoders, controllers), which are incurred per event.64 This overhead can be substantial, especially at high event rates.93
Fixed Latency Assumption: Analytical models like ZigZag typically use fixed, deterministic costs for operations (e.g., cycles per MAC, cycles per memory access). In event-driven systems, particularly those with asynchronous components or shared resources like queues, the latency of processing an event can be variable, depending on factors like network congestion, queue occupancy, and resource contention.212 Average-case or statistical modeling might be required, moving away from simple cycle counting.
Simplified PE/NoC Models: The standard PE model in ZigZag is often a basic MAC unit. Event-driven PEs might have additional complexity related to event processing or state management.95 Similarly, standard NoC models may not capture the nuances of asynchronous protocols, flow control, or multicast efficiency critical to event-based communication.65
3.3 Manifestation in Dense ANN ExecutionCrucially, these differences between event-driven and synchronous execution models persist even when the accelerator is tasked with executing a conventional ANN with dense weights and activations:
Computation Triggering: Although the ANN layer might perform dense MAC operations internally, the initiation of these operations on an event-driven accelerator is still triggered by the arrival of input data packaged as events. For example, processing the outputs for a specific location in a convolutional layer might only begin once the required input activation event(s) arrive at the PE. The timing and energy cost associated with this event reception, decoding, and dispatch are present regardless of the density of the subsequent computation.
PE Utilization and Latency: While the PE might perform dense computations once triggered, the overall layer latency and PE utilization are governed by the flow of events. If events arrive sporadically or face contention in queues or the NoC, PEs might idle, impacting performance. Latency is not simply the time for dense computation divided by parallelism, but includes event handling delays, queueing times, and communication latencies. Stalls can occur due to event backpressure, not just memory bandwidth limitations as typically modeled in ZigZag.
Memory Access Pattern: Memory accesses for weights and activations are initiated based on processed events. While the sequence of addresses accessed might resemble a dense pattern if events trigger computation for all output locations, the timing of these accesses is dictated by the event flow. Furthermore, the overhead associated with calculating memory addresses might be tied to the event decoding process rather than loop counters.
Energy Consumption: The total energy includes not only the MAC operations and associated data movement (which ZigZag models) but also the energy consumed by the event handling logic (controllers, queues, NoC interfaces) which is active whenever events are being processed.64 Additionally, event-driven systems might employ power gating during periods of inactivity (no events), which requires specific modeling to capture potential energy savings.148 Asynchronous components also have different power characteristics than synchronous ones.212
In essence, even when executing dense ANNs, an event-driven accelerator operates under a different control paradigm than a synchronous, loop-based accelerator. The fundamental unit of work scheduling shifts from loop iterations to events, introducing new sources of overhead and different performance dynamics that require explicit modeling beyond the capabilities of standard ZigZag/Stream.4. Proposed Modifications to ZigZag/Stream for Event-Driven ANN ModelingTo accurately model event-driven accelerators like Seneca executing dense ANNs, the ZigZag/Stream framework requires significant conceptual modifications across its core components. These changes aim to shift the modeling paradigm from being purely loop-driven and synchronous to being event-aware and capable of handling potential asynchronicity and associated overheads.4.1 Workload Representation ChangesThe representation of the ANN workload needs to incorporate event-driven semantics:
Event Trigger Condition: Layer or operator definitions should be augmented to specify the condition that triggers computation. For ANNs, this would typically be the arrival of one or more input activation "events" (even if all possible activations arrive in a dense scenario). This explicitly signals that computation is data-driven, not purely scheduled by loop counters.
Activation Representation: While the ANN activations are dense, the representation could optionally model them as a stream of events, each carrying an activation value and its coordinates (or sequence identifier). This reflects how an event-driven PE might receive its inputs sequentially or in packets, rather than assuming parallel access to an entire tile based on loop indices.
Layer Dependencies: The existing directed acyclic graph (DAG) representation used in Stream for layer fusion should be maintained, but the interpretation should emphasize the flow of activation events between dependent layers or computational nodes mapped across cores.
4.2 Hardware Architecture ExtensionsThe hardware model definition needs to be extended to include components specific to event-driven processing:
Event Handling Components: Introduce new architectural primitives:

EventQueues: Model FIFO buffers for incoming/outgoing events. Parameters should include depth (capacity), width (bits per event), energy cost per enqueue/dequeue operation, access latency, and potentially policies for handling full/empty conditions.
EventController: Represent the logic managing event flow (e.g., Seneca's RISC-V + Loop Controller combination 95). Parameters should capture its static power, dynamic energy per event processed (for decoding, scheduling, etc.), and the latency introduced per event.


Processing Element (PE) Model Modification:

Introduce parameters for the energy and latency overhead associated with receiving an event trigger and initiating the corresponding computation (e.g., loading micro-code, setting up MAC unit). This cost is separate from the energy/latency of the MAC operation itself.
Allow specification of specialized PE capabilities relevant to event processing, such as event buffering or optimized handling of grouped events (like spike-grouping 93), with associated cost/performance parameters.


Memory System Model:

Memory access latency and energy models should potentially become dependent not just on the memory level but also on event queueing dynamics or contention, especially for shared memory resources accessed via event-triggered requests.
Add support for modeling specialized memory interfaces or prefetch units designed for asynchronous or event-based access patterns (e.g., Seneca's SMPU 95).


Network-on-Chip (NoC) Model:

Enable specification of asynchronous NoC protocols and their associated parameters (e.g., handshake overhead, flow control mechanisms).65
Model NoC latency not just based on hop count and bandwidth, but also considering packetization overhead (potentially smaller packets for events), contention based on event traffic rates, and asynchronous protocol delays.
Include specific models for the energy cost of asynchronous links (per bit or per packet).
Explicitly model the efficiency and cost of NoC multicast capabilities if present.65


4.3 Cost Model AdaptationThe core cost estimation engine requires fundamental changes to reflect the event-driven execution model:
Event Handling Overhead: Introduce explicit cost terms added to the total energy and latency calculations:

Eevent_handle​: Total energy consumed by Event Controllers and Event Queues, calculated based on the number of events processed, static power, and per-event dynamic energy costs.64
Levent_handle​: Total latency contribution from event handling logic, calculated based on per-event processing delays and potential queueing delays.


Latency Calculation: This is the most significantly impacted area. The purely loop-bound calculation of ZigZag must be replaced or heavily augmented by an event-flow model:

Model Foundation: Latency should be modeled as a function of event arrival rates, queueing delays (potentially using basic queuing theory or statistical models), event controller processing time, PE computation time (triggered by events), and NoC communication latency (including asynchronous effects).212
Triggering: The start time for any computation within a PE depends on the arrival time of the triggering event(s) and any preceding queueing/controller delay.
End-to-End Latency: Overall layer or network latency depends on the critical path through this event-driven flow, considering potential parallel processing and synchronization points (if any).
Asynchronicity: For asynchronous components, latency should be modeled probabilistically or using average-case estimates that account for contention and variability, rather than fixed cycle counts. Analytical models for asynchronous systems often involve approximations or statistical methods.223


Energy Calculation:

Activity-Based: Energy calculation should be based on the actual activity triggered by events. Sum the energy of:

Computations (MACs) actually performed.
Data movements (memory accesses, NoC transfers) triggered by events.
Event handling logic (controllers, queues).


Power Gating: If the hardware model includes power gating for idle components (when no events are processed), the energy model should incorporate these potential savings based on estimated idle times derived from event rates.148
Component Costs: Use specific energy costs for asynchronous communication links and specialized event handling components.


4.4 Mapping and Search ConsiderationsThe mapping representation and the search process need to adapt to the event-driven paradigm:
Mapping Representation: The mapping definition (spatial tiling, temporal loop order) needs to be extended to include parameters related to event management, such as allocation of events to specific queues or scheduling priorities for event processing.
Search Objectives: The DSE should consider objectives beyond minimizing total energy/latency. New objectives could include minimizing maximum event queue occupancy (to avoid stalls), balancing event processing load across PEs/cores, or minimizing inter-core event communication traffic.
Search Space Trade-offs: The interaction between traditional spatial mapping (tiling) and event handling creates new optimization challenges. For example, large computational tiles might improve MAC efficiency but could lead to bursty event generation, potentially overwhelming event queues or controllers. Conversely, small tiles might smooth event traffic but increase the relative overhead of event handling per computation. The search algorithm needs to navigate these new trade-offs.
New Search Heuristics: Heuristics guiding the search process should be developed to prioritize mappings that avoid event bottlenecks, effectively utilize asynchronous communication bandwidth, or optimize the flow of events through the modeled queues and controllers. Gradient-based search might be adapted if differentiable models for queueing or contention can be formulated.3
