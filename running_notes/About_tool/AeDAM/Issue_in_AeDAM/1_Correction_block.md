## Detailed explanation of the problem

### ✅ In an event-driven architecture **(like the one you're modeling)**:

* **Each input event triggers** a burst of computations.
* The **input** is fetched once and **reused fully** in registers or buffers until all relevant MACs are done — **no repeated fetches**.
* The **weights** are either already prefetched or streamed as needed **per event**, and reused repeatedly for all outputs affected by that input.
* Therefore:

| Operand     | Expected access pattern (event-driven)                                                   |
| ----------- | ---------------------------------------------------------------------------------------- |
| **Inputs**  | Accessed once → Reused (perfect)                                                         |
| **Weights** | Accessed per-event → Reused in RF/SRAM                                                   |
| **Outputs** | Accessed repeatedly across tiles (partial sums), so prone to inflation in ZigZag’s model |

---

### 🔍 So why are input & weight accesses correct, but output isn't?

ZigZag models **repetition of output accumulation** (due to tiling, partial sums, etc.) even in event-driven mode, because it’s not aware that:

> *“Each event completely finishes the output(s) it affects and never needs to touch them again.”*

So:

* ✅ Inputs & Weights behave naturally like in an event-driven model.
* ❌ Outputs are still treated like in a **frame-based schedule**, where intermediate partials are written and later re-read.

---

### 🧠 Final Takeaway:

> **Yes, your input and weight access counts are accurate** because the mapping and access style you've used (temporal loops, operand placement) align with event-driven semantics — ZigZag doesn't inflate these due to its own internal tiling logic.

Only **output word accesses** need external correction to align with the true event-driven behavior you're targeting.

# Event-Driven DSE Area Model Documentation

This document provides the complete area estimation model for event-driven neural network accelerators, calibrated from SENECA architecture data and validated against literature.

## Overview

The area model estimates silicon area for event-driven neuromorphic processors by accounting for:
- SRAM arrays with multiple port configurations
- Register files for small, highly-ported storage
- Event-driven architectural overhead (NoC, event generation, control logic)
- Technology scaling effects

**Key Features:**
- Calibrated from SENECA (GF 22nm) actual measurements
- Supports multi-port memory configurations
- Accounts for event-driven processing overhead
- Scalable across technology nodes

---

## Base Constants

### Technology Constants (GF 22nm FDX)

| Constant | Value | Unit | Description | Source |
|----------|-------|------|-------------|---------|
| `A_cell_sram` | **0.165** | µm²/bit | Single-port SRAM bit-cell area | SENECA Table 2 |
| `A_cell_rf` | **3.6** | µm²/bit | Register file (flip-flop) area | SENECA Table 2 |
| `A_overhead_small` | **1,500** | µm² | Peripheral overhead for arrays < 8KB | Calibrated |
| `A_overhead_large` | **800** | µm² | Peripheral overhead for arrays ≥ 8KB | Calibrated |
| `tech_node_ref` | **22** | nm | Reference technology node | SENECA |

### Event-Driven Architecture Overhead

| Component | Area | Unit | Description | Source |
|-----------|------|------|-------------|---------|
| `noc_router` | **12,100** | µm² | Network-on-chip router per core | SENECA Table 7 |
| `event_generator` | **9,700** | µm² | Event generation logic | SENECA Table 7 |
| `loop_buffer` | **10,500** | µm² | Loop buffer and control | SENECA Table 7 |

---

## Formula Definitions

### 1. Technology Scaling Factor

```
tech_scale = (target_node / reference_node)²
```

Where:
- `target_node`: Target technology node (nm)
- `reference_node`: 22 nm (reference)

### 2. Port Factor Calculation

For memory port configuration (R read ports, W write ports, RW read-write ports):

```
F_port = 1 + port_multiplier × (total_ports - 1) / 3 + write_penalty
```

Where:
- `total_ports = R + W + RW`
- `port_multiplier = 0.27` (calibrated from SENECA 4-port data)
- `write_penalty = 0.05 × W` if W > 1, else 0

**Special Cases:**
- Single port (total_ports ≤ 1): `F_port = 1.0`
- High port count (total_ports > 4): `F_port = min(total_ports × 0.8, total_ports)`

### 3. SRAM Area Calculation

```
A_sram = tech_scale × [A_overhead + capacity_bits × A_cell_sram × F_port] × word_correction
```

Where:
- `A_overhead = A_overhead_small` if capacity < 8KB, else `A_overhead_large`
- `word_correction = 1 + 0.03 × |log₂(word_width / 64)|`

### 4. Register File Area Calculation

```
A_rf = tech_scale × capacity_bits × A_cell_rf
```

*Note: Use for memories ≤ 2KB with ≥ 3 ports*

### 5. Total Core Area

```
A_total = A_memories + A_logic_overhead + A_event_driven_overhead
```

Where:
- `A_logic_overhead = 10,900 µm²` (RISC-V + basic logic)
- `A_event_driven_overhead = 37,700 µm²` (event-specific components)

## Implementation Functions

### Core Area Estimation Function

```python
def sram_area_um2(capacity_bits, read_ports=1, write_ports=1, rw_ports=0, 
                  word_width=64, tech_node=22):
    """
    Calculate SRAM area with multi-port support
    
    Parameters:
    -----------
    capacity_bits : int
        Memory capacity in bits
    read_ports : int, default=1
        Number of independent read ports
    write_ports : int, default=1  
        Number of independent write ports
    rw_ports : int, default=0
        Number of read-write ports
    word_width : int, default=64
        Memory word width in bits
    tech_node : int, default=22
        Technology node in nm
        
    Returns:
    --------
    float
        Area in µm²
    """
    
    # Technology scaling
    tech_scale = (tech_node / 22.0) ** 2
    
    # Base parameters
    A_cell = 0.165 * tech_scale  # µm²/bit
    
    # Overhead selection
    if capacity_bits < 8 * 1024:
        A_overhead = 1500 * tech_scale
    else:
        A_overhead = 800 * tech_scale
    
    # Port factor calculation
    total_ports = read_ports + write_ports + rw_ports
    if total_ports <= 1:
        F_port = 1.0
    elif total_ports <= 4:
        base_factor = 1.0 + 0.27 * (total_ports - 1) / 3
        write_penalty = 0.05 * write_ports if write_ports > 1 else 0
        F_port = base_factor + write_penalty
    else:
        F_port = min(total_ports * 0.8, total_ports)
    
    # Word width correction
    import math
    word_correction = 1 + 0.03 * abs(math.log2(word_width / 64))
    
    # Final calculation
    area = A_overhead + capacity_bits * A_cell * F_port
    return area * word_correction
```

### Complete Core Area Function

```python
def total_core_area_mm2(memory_config, core_type='event_driven'):
    """
    Calculate total core area including all components
    
    Parameters:
    -----------
    memory_config : dict
        Dictionary defining memory hierarchy
    core_type : str, default='event_driven'
        Core type: 'event_driven' or 'traditional'
        
    Returns:
    --------
    float
        Total core area in mm²
    """
    
    total_area_um2 = 0
    
    # Process each memory level
    for mem_name, mem_spec in memory_config.items():
        if mem_spec['type'] == 'sram':
            area = sram_area_um2(
                capacity_bits=mem_spec['capacity_bits'],
                read_ports=mem_spec.get('read_ports', 1),
                write_ports=mem_spec.get('write_ports', 1),
                rw_ports=mem_spec.get('rw_ports', 0),
                word_width=mem_spec.get('word_width', 64)
            )
        elif mem_spec['type'] == 'register_file':
            # Register file area (for small, highly-ported memories)
            tech_scale = (22.0 / 22.0) ** 2  # Adjust if different tech
            area = mem_spec['capacity_bits'] * 3.6 * tech_scale
        else:
            area = 0
            
        total_area_um2 += area
    
    # Add fixed logic overhead
    total_area_um2 += 10900  # µm² for RISC-V + basic logic
    
    # Add event-driven overhead if applicable
    if core_type == 'event_driven':
        total_area_um2 += 37700  # µm² for event-driven components
    
    # Convert to mm²
    return total_area_um2 / 1e6
```

#### What the numbers in your trace mean

* `wr ^ = 6 021 120` vs `rd ^ = 607 488` at Level 1
  – \~10 % of partial sums end up in Level-1 SRAM and later get read out once.
  – That matches a **small-RF / buffered-output** variant of event-driven hardware rather than the pure “register-fire” path described for vanilla SENECA.

Consequently your corrected rule set—**keep** that Level-1 `rd ^`, zero everything else listed above—accurately reflects the traffic pattern of an event-driven core that:

1. Spills partial sums locally when RF capacity is exceeded.
2. Emits its *completed* outputs from the same local SRAM (not directly from the RF).
3. Never accepts backward traffic from higher levels.

### Final algorithm (in prose)

1. **Iterate** over every `(operand, level, access_type)` triple.
2. **If operand ≠ `O`** → include the energy normally.
3. **If operand = `O`:**

   * **Level 0 (register-file):** always include all four access types.
   * **Level 1 (SRAM):**

     * **Ignore** `wr v` (NoC→SRAM back-write).
     * **Optionally ignore** `rd ^` if your target design “fires from RF”; otherwise keep it.
     * Always include `rd v`, `wr ^` (RF↔SRAM spill traffic).
   * **Level 2 (NoC):**

     * **Ignore** `rd v`.
     * **Include** `wr ^` (one packet per fired output).
4. Multiply the kept access counts by their per-access energy to get dynamic energy.

Parameterising that one *conditional* (`keep_rd_hat_level1`) lets you cover both SENECA-style “register-fire” cores (set it to **False**) and buffered-output variants such as your current mapping (set it to **True**).

With this rule set you eliminate only the transfers that do **not** occur in any event-driven architecture, while retaining those that appear in practical implementations when RF capacity is limited.

#### Algorithm for Static Power Calculation

```python
class StaticPowerCalculator:
    def __init__(self, memory_pool, technology_node=22e-9):
        self.memory_pool = memory_pool
        self.tech_node = technology_node
        
        # Technology-dependent leakage parameters (per bit)
        self.leakage_density = {
            'SRAM': 10e-12,      # 10 pW/bit (from SENECA paper)
            'Register': 600e-12,  # 600 pW/bit 
            'STT-MRAM': 0,       # Non-volatile
            'DRAM': 1e-12        # 1 pW/bit (off-chip)
        }
    
    def calc_memory_static_power(self, memory_instance):
        """Calculate static power for a single memory instance"""
        mem_type = memory_instance.memory_type
        size_bits = memory_instance.size * 8  # Convert bytes to bits
        unroll_count = memory_instance.unroll_count
        
        # Base leakage per bit
        leakage_per_bit = self.leakage_density[mem_type]
        
        # Technology scaling (smaller nodes = higher leakage density)
        tech_scaling = (22e-9 / self.tech_node) ** 2
        leakage_per_bit *= tech_scaling
        
        # Total static power for this memory
        return size_bits * unroll_count * leakage_per_bit
    
    def calc_total_static_power(self, accelerator):
        """Calculate total static power for entire accelerator"""
        total_static = 0
        
        # Memory hierarchy static power
        for mem_level in accelerator.memory_hierarchy.mem_level_list:
            mem_static = self.calc_memory_static_power(mem_level.memory_instance)
            total_static += mem_static
            
        # MAC array static power (from operational array)
        mac_static = accelerator.operational_array.static_power
        total_static += mac_static
        
        # Control logic static power (RISC-V, controllers)
        control_static = self.estimate_control_static_power(accelerator)
        total_static += control_static
        
        return total_static
    
    def estimate_control_static_power(self, accelerator):
        """Estimate static power of control logic"""
        # Rough estimate: ~10% of total (from SENECA paper)
        # More sophisticated models would analyze actual logic gates
        return accelerator.operational_array.static_power * 0.1
```

```python
        pareto_points = []

                    break

                metrics_a['execution_time'] <= metrics_b['execution_time'] and
```

Great question! You're right to be confused about this. Let me clarify the **fundamental difference** between static power calculation and how it changes across DSE points.

## Static Power Reality Check

### What Static Power Actually Represents:
- **Static power = Leakage current × Supply voltage**
- It's the power consumed **just by having the transistors exist** (regardless of activity)
- Every SRAM cell, every flip-flop, every gate leaks a tiny amount of current
- **It flows 24/7 as long as power is on**

### Why It's Just Capacity × Leakage Density:
```
Static Power = Total_Transistors × Leakage_per_Transistor
            ≈ Memory_Capacity × Leakage_per_bit
```

This is because:
- Each stored bit requires ~6 transistors (in SRAM)
- Larger memories = more transistors = more leakage
- **Width, ports, latency don't add transistors for storage**

## How Static Power Changes Across Your DSE Points

Looking at your examples:

```
Point A: 2097152 bits, 128-bit width, 4 ports, 2 cycles, 0.18 pJ/bit
Point B: 524288 bits,  256-bit width, 4 ports, 1 cycle, 0.36 pJ/bit
```

### Static Power Calculation:
- **Point A**: `2097152 × 10e-12 W = 21.0 μW`
- **Point B**: `524288 × 10e-12 W = 5.2 μW`

**Only capacity matters!** The 4× capacity difference gives 4× static power difference.

### What About Width/Ports/Latency?
- **Width (128 vs 256)**: Affects peripheral circuits (sense amps, muxes) - small static impact
- **Ports (4 ports)**: Adds port circuitry - small static impact  
- **Latency (2 vs 1 cycles)**: Usually just changes timing constraints - **no static impact**
- **Dynamic energy (0.18 vs 0.36 pJ/bit)**: **Zero correlation with static power**

## The Event-Driven Twist

In your **event-driven exploration**, static power becomes **more critical** because:

### 1. **Low Activity = High Static Fraction**
```python
# Sparse neuromorphic workload
activity_rate = 0.01  # Only 1% of time active
dynamic_power = 100e-6 * activity_rate = 1 μW
static_power = 21 μW  # Always on!
static_fraction = 21/(21+1) = 95%!
```

### 2. **Memory Sizing Trade-offs**
```python
# Large memory (better for reuse, fewer DRAM accesses)
large_mem_static = 2097152 * 10e-12 = 21 μW
large_mem_dynamic = fewer_dram_accesses * dram_energy

# Small memory (more DRAM traffic)  
small_mem_static = 524288 * 10e-12 = 5.2 μW
small_mem_dynamic = more_dram_accesses * dram_energy

# Which is better depends on event sparsity!
```

### 3. **Static Energy Accumulation**
```python
def calc_total_energy_event_driven(capacity_bits, execution_cycles, clock_freq):
    # Static power (always consuming)
    static_power = capacity_bits * 10e-12  # W
    
    # Execution time
    exec_time = execution_cycles / clock_freq  # seconds
    
    # Static energy accumulates over entire execution
    static_energy = static_power * exec_time  # Joules
    
    return static_energy
```

## Key Insights for Your DSE:

1. **Static power scales ONLY with capacity** - ignore width/ports/latency for static calculation

2. **Smaller memories aren't always better** in event-driven systems:
   - Less static power ✓
   - But may cause more DRAM traffic ✗
   - Net energy depends on sparsity level

3. **Long execution times amplify static energy**:
   - Sparse events → longer execution
   - More time for static energy to accumulate

4. **Memory hierarchy optimization becomes critical**:
   - Right-size each level for your sparsity pattern
   - Consider power-gating unused portions

**Bottom line**: In event-driven systems, static power dominance makes capacity the most important parameter for energy optimization, often more than dynamic energy efficiency!
